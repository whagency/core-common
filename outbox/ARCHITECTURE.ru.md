# Разбор кода

Пошаговая экскурсия по рантайму outbox: что выполняется, в каком порядке и какой
отказ предотвращает каждый элемент. Про использование, конфигурацию и
эксплуатацию — в [README.ru.md](README.ru.md).

*English version: [ARCHITECTURE.md](ARCHITECTURE.md)*

Прочитать сверху вниз один раз; дальше достаточно графа вызовов.

```
ПУТЬ ЗАПИСИ  (внутри бизнес-транзакции, по одному на side effect)
  controller.enqueueXxx
    └─ postgres.Repository.Create ──────────────► INSERT … ON CONFLICT DO NOTHING

СТАРТ  (composition root)
  NewRegistry → Register(handler)…
  NewWorker(repo, registry, cfg) → WorkerConfig.applyDefaults
  NewPool(worker, cfg)           → PoolConfig.applyDefaults → queueSizeFor
  errgroup.Go(pool.Run)

РАНТАЙМ  (Workers + 1 горутина)
  Pool.Run
    ├─ горутина relay
    │    Pool.safeClaimUntilDrained   (recover → OnClaimError)
    │    └─ Pool.claimUntilDrained
    │      ├─ Pool.claimBudget
    │      ├─ sleepCtx                      (насыщение: ждём слот)
    │      └─ Pool.relayOnce
    │           ├─ Worker.Claim ───────────► UPDATE … FOR UPDATE SKIP LOCKED … RETURNING
    │           ├─ Pool.tryAcquireInFlight
    │           └─ Pool.submit ─────────────► канал очереди
    │
    └─ горутины воркеров ×Workers
         ◄── канал очереди
         Pool.safeProcessOne
           ├─ defer Pool.releaseInFlight
           ├─ defer recover → Worker.DeadLetter
           └─ Worker.ProcessOne → Worker.process
                ├─ Registry.Dispatch → Handler.Handle
                └─ Worker.withStatusCtx → repo.Mark{Delivered,Failed,Dead}
                                            └─ ownedByWorker → applyStatusUpdate

ОСТАНОВКА
  ctx отменён → воркеры Pool.drain → relay выходит → wg.Wait → Run возвращается

CRON  (регистрирует сервис, не библиотека)
  Repository.Prune             — ограниченный цикл GC
  Repository.OldestPendingAge  — метрика лага
```

---

## 1. Путь записи

### `controller.enqueueXxx` → `Repository.Create`

Вызывается изнутри бизнес-транзакции, между `Begin` и `Commit`:

```go
ctx = c.dbTransactionManager.Begin(ctx)
c.depositRequests.WithTxFromContext(ctx).Create(ctx, &depositRequest)  // бизнес-состояние
c.enqueueDepositCounter(ctx, depositRequest)                          // намерение
return c.dbTransactionManager.Commit(ctx)
```

Сборщики строк (`buildCounterOutboxParams`, `buildNotificationPushOutboxParams` в
account-service) только собирают `CreateParams`. Они живут в пакете контроллеров,
потому что решение *что именно* отправлять — бизнесовое; а хендлеры, которые потом
это доставляют, относятся к транспорту и лежат в `internal/transport/outbox`.

### `postgres.Repository.Create`

Три намеренные детали:

**Он сам достаёт транзакцию** через `commondb.GetTxFromContext(ctx)`, а не требует
от вызывающего цепочку `WithTxFromContext`. Забытая цепочка пишет строку в базовое
соединение, и тогда side effect переживает откат бизнес-транзакции — тихий отказ
без локальных симптомов. Гарантия слишком важна, чтобы держаться на договорённости.

**Он опускает `next_attempt_at` и `created_at`**, чтобы сработал их `DEFAULT NOW()`.
`ClaimDue` сравнивает `next_attempt_at` с часами **базы**; проставление их из часов
приложения поставило бы право на захват в зависимость от расхождения между ними, и
под, идущий на миллисекунды впереди, молча откладывал бы собственные свежие
сообщения.

**Цель конфликта прибита к `dedupe_key`.** Голый `DO NOTHING` проглатывал бы также
нарушения любого ограничения, добавленного позже, молча теряя строки.

`withoutImplicitTx` отключает неявную транзакцию записи в GORM. Каждая запись здесь
— один оператор, который PostgreSQL и так выполняет атомарно, поэтому обёртка даёт
только раунд-трипы `BEGIN`/`COMMIT` — измерено примерно в 2.7× стоимости самого
оператора.

## 2. Старт

### `NewWorker` → `WorkerConfig.applyDefaults`

Заполняет нулевые значения и обеспечивает один инвариант:

```go
if c.HandlerTimeout+statusUpdateGrace > c.Lease {
    c.Lease = c.HandlerTimeout + statusUpdateGrace
}
```

Хендлер, способный пережить собственную аренду, гарантирует двойную обработку:
строка становится перезахватываемой, пока первый воркер ещё внутри неё. `NewWorker`
пишет warning, когда ему приходится поднять аренду — этот warning означает, что
конфигурация попросила небезопасное.

### `NewPool` → `queueSizeFor`

`PoolConfig.applyDefaults` заполняет только `Workers` и `RelayInterval`. Ёмкость
канала **выводится**, а не настраивается:

```go
queueSize = Workers × (Lease − HandlerTimeout − statusUpdateGrace) / HandlerTimeout
```

Захваченное сообщение держит аренду, пока стоит в канале, поэтому аренда обязана
покрывать задержку в очереди. Больше — и аренды истекают на просто стоящих
сообщениях; меньше — только страдает пропускная способность. Результат ноль
означает, что аренда не позволяет очередь вовсе, и канал становится
небуферизованным: передача завершается только когда воркер действительно готов
принять.

## 3. Relay

Одна горутина, единственная, которая читает базу. Именно это гарантирует, что
второго одновременного захвата не бывает — без блокировок и выбора лидера.

`Run` вызывает его через `safeClaimUntilDrained`, который перехватывает паники.
Хендлеры такую защиту уже получают от `safeProcessOne`; без такой же для relay
паника в пути захвата — баг драйвера, неожиданный тип колонки — уронила бы
процесс, который заодно отвечает по HTTP и gRPC. Вставший relay при живом
сервисе, о котором сообщает `OnClaimError`, — режим отказа лучше.

### `Pool.claimUntilDrained`

```go
for ctx.Err() == nil {
    budget := p.claimBudget()
    if budget <= 0 {
        if !sleepCtx(ctx, saturatedPollInterval) { return }
        continue
    }
    if !p.relayOnce(ctx, budget) { return }
}
```

Два выхода, и разница между ними принципиальна:

- **Бюджет нулевой** — пул полон. Насыщение преходяще, поэтому он ждёт слот 25 мс,
  а не возвращается. Возврат здесь отдал бы разбираемый бэклог тикеру и застопорил
  его на целый `RelayInterval`.
- **`relayOnce` вернул false** — захват пришёл неполным, значит в базе больше
  ничего не готово. *Вот это* и есть причина спать до следующего тика.

`Run` вызывает это один раз до входа в цикл тикера, поэтому под, стартующий с
готовым бэклогом, начинает работать сразу, а не простаивает интервал.

### `Pool.claimBudget`

```go
queueSize + Workers − len(inFlight)
```

Сколько ещё сообщений пул может взять прямо сейчас: все слоты очереди плюс все
слоты воркеров, минус то, что он уже держит. Захват сверх этого запускает аренды,
которые пул не успеет отработать до их истечения.

### `Pool.relayOnce`

Захватывает до `want`, затем для каждого сообщения:

1. `tryAcquireInFlight(msg.ID)` — отвергает сообщение, которое этот инстанс уже
   обрабатывает. Это не паранойя: `locked_by` одинаков для всех воркеров одного
   процесса, поэтому база не может отличить собственный перезахват этого инстанса
   от законного. Без этого множества сообщение, всё ещё стоящее в канале, могло бы
   быть перезахвачено и отправлено в обработку второй раз.
2. `submit` — блокируется на полном канале. Эта блокировка **и есть**
   back-pressure: relay не может обогнать воркеров, а число горутин остаётся
   фиксированным.

Возвращает `len(msgs) == want`, то есть «захват был полным, вероятно есть ещё».
Возврат чего-либо другого прекратил бы разбор раньше времени — ровно эта ошибка
однажды ограничила пропускную способность одним батчем на тик.

## 4. Воркеры

### `Pool.safeProcessOne`

```go
defer p.releaseInFlight(msg.ID)
defer func() {
    if r := recover(); r != nil {
        log…
        p.worker.DeadLetter(ctx, msg, fmt.Sprintf("handler panic: %v", r))
    }
}()
p.worker.ProcessOne(ctx, msg)
```

`recover` не даёт паникующему хендлеру убить горутину воркера и отправляет
сообщение в dead-letter. Оставленное в `processing`, оно перезахватывалось бы при
каждом истечении аренды вечно, паникуя каждый раз, и ни разу не вызвав `OnDead` —
невидимый горячий цикл.

### `Worker.process` — лестница решений

Порядок здесь и есть дизайн: каждый шаг существует потому, что нижний дал бы
неверный ответ.

**1. Бюджет уже исчерпан → dead, без диспатча.**

```go
if msg.Attempts >= msg.MaxAttempts { deadLetter(…); return }
```

Воркер, умирающий посреди хендлера, никогда не возвращает ошибку, а значит никогда
не доходит до проверки бюджета после хендлера. Перезахваты по протухшей аренде
расходуют бюджет вместо него (см. `ClaimDue`), и здесь сообщение, которое раз за
разом убивает своего воркера, наконец завершается.

**2. Диспатч под `HandlerTimeout`.** Дедлайн применяется только к `handlerCtx`.
Обновления статуса используют другой контекст (шаг 4), поэтому отвалившийся по
таймауту хендлер всё равно может записать свой исход.

**3. `OnHandlerDuration` срабатывает независимо от результата** — гистограмма
латентности, видящая только успехи, скрыла бы ровно ту деградацию, которую вы
хотите поймать.

**4. Успех → `MarkDelivered`.** Обратите внимание на порядок в масштабе всей
системы: сначала происходит side effect, потом помечается строка. Обратный порядок
дал бы at-most-once — тихую потерю. Именно этот порядок делает гарантию
at-least-once и объясняет, почему хендлеры обязаны быть идемпотентны.

**5. `ctx.Err() != nil` → оставить сообщение в покое.** Наша собственная остановка
не является отказом доставки. Запись его сожгла бы попытку и отодвинула сообщение
на полный backoff; оставленная строка в `processing` стоит только истечения аренды
и сохраняет бюджет — тот же путь, которым уже идёт жёсткое падение. Эта проверка
стоит **выше** классификации ошибки намеренно. Истечения `HandlerTimeout` это не
касается: оно отменяет `handlerCtx`, а не `ctx`.

**6. `ErrNonRetryable` → сразу dead**, бюджет не тронут. Битый payload или
незарегистрированный `event_type` не станут валидными на ретрае; десять попыток на
них только оттянут алерт.

**7. Бюджет исчерпан → dead.** `msg.Attempts + 1 >= msg.MaxAttempts`, поэтому
`MaxAttempts = N` даёт ровно N выполнений хендлера.

**8. Иначе → `MarkFailed`** с `backoff(attempt)`: экспонента от `BaseBackoff` с
потолком `MaxBackoff` и джиттером ±10%, чтобы инстансы не ретраились в унисон.
Потолок применяется до конверсии `float64 → Duration`, поэтому переполнение
невозможно.

### Запись статуса

`withStatusCtx` выполняет обновление под `context.WithoutCancel(ctx)` с дедлайном
`statusUpdateGrace`. Без этого каждое сообщение в полёте, которое **успешно**
отработало во время SIGTERM, провалило бы запись статуса и было бы переотправлено
при следующем старте.

`ownedByWorker` ограничивает обновление:

```sql
WHERE id = ? AND locked_by = ? AND locked_until > NOW()
```

`applyStatusUpdate` превращает нулевой результат в `ErrLeaseLost`. Вместе это
означает, что воркер, чью аренду уже перехватили, выбрасывает собственный
результат вместо того, чтобы затереть состояние нового владельца — а обновление
нуля строк никогда не принимается за успех. `logStatusErr` отделяет потерю аренды
(безобидную, ей владеет кто-то другой) от настоящего сбоя записи.

## 5. Остановка

`ctx` отменяется errgroup'ой по SIGTERM.

Воркеры попадают в `case <-ctx.Done()` и вызывают `Pool.drain`, который дочищает
то, что уже лежит в канале, используя **свежий** контекст с бюджетом в один
`HandlerTimeout`. Выполнение этих хендлеров под отменённым контекстом было бы хуже,
чем не разбирать очередь вовсе: каждый упал бы мгновенно, сжёг попытку и уехал на
полный backoff, тогда как брошенное сообщение просто дожидается истечения аренды с
нетронутым бюджетом. Что не уложилось в бюджет — остаётся в канале и уходит на
истечение аренды, ту же страховку, что покрывает жёсткое падение.

Relay выходит по `ctx.Done()`, `wg.Wait()` отпускает, `Run` возвращает nil.

## 6. Cron-джобы

Регистрирует сервис, а не библиотека.

**`Repository.Prune(deliveredOlderThan, deadOlderThan)`** удаляет батчами по 5000,
чтобы GC никогда не держал блокировки на большой таблице долго. Два retention'а
потому, что строки служат разным целям: доставленные забивают диск, мёртвые — это
запись об инциденте, и они обязаны пережить время, нужное оператору на реакцию.
Доставленные стареют от `delivered_at` (это же позволяет частичному GC-индексу
обслуживать скан), мёртвые — от `created_at`.

Безопасен рядом с активными воркерами: ни один из этих статусов не захватываем.

`Prune` захватывает свои батчи через `FOR UPDATE SKIP LOCKED`, потому что у
платформенного cron нет выбора лидера: джобу выполняет каждый под. Без этого
конкурентные уборщики сериализуются на блокировках строк друг друга, и N подов
делают работу одного.

**`Repository.OldestPendingAge`** питает gauge. Счётчики не обнаружат вставший
relay — он просто перестаёт их инкрементить, что неотличимо от простоя. Сбрасывайте
gauge на каждом замере: типы событий с разобранным бэклогом отсутствуют в карте, и
`GaugeVec` иначе вечно показывал бы последнее значение.

## 7. Где живёт каждая гарантия

| Гарантия | Чем обеспечена |
|---|---|
| Намерение атомарно бизнес-состоянию | `Create` внутри транзакции вызывающего |
| Нет дублей строк на одно логическое событие | `UNIQUE (dedupe_key)` + `ON CONFLICT DO NOTHING` |
| Один захватчик между инстансами | `FOR UPDATE SKIP LOCKED` |
| Один диспатч внутри инстанса | `Pool.inFlight` |
| Устаревший писатель не затрёт нового владельца | `ownedByWorker` + `ErrLeaseLost` |
| Ничего не теряется при смерти пода | Истечение `locked_until` + ветка перезахвата в `ClaimDue` |
| Ядовитые сообщения завершаются | `attempts` при перезахвате + проверка бюджета до диспатча |
| Паники хендлеров завершаются | `recover` в `safeProcessOne` → `DeadLetter` |
| Паника в relay не роняет сервис | `recover` в `safeClaimUntilDrained` → `OnClaimError` |
| Конкурентные уборщики не блокируют друг друга | `FOR UPDATE SKIP LOCKED` в `Prune` |
| Память и горутины ограничены под нагрузкой | Блокирующий `submit`, фиксированные `Workers+1` |
| Остановка ничего не стоит | Проверка `ctx.Err()` + `drain` со свежим контекстом |
