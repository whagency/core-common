# outbox

Транзакционный outbox для надёжной доставки post-commit side effects — публикаций
в очередь, gRPC-вызовов в другие сервисы, уведомлений — в Go-сервисах app.

*English version: [README.md](README.md)*

Задача, которую он решает: бизнес-транзакция закоммитилась, а последующий вызов
упал. Без outbox этот side effect просто теряется, и нигде в системе не записано,
что он должен был произойти. С outbox намерение пишется в той же транзакции, что
и бизнес-состояние, поэтому происходит либо и то и другое, либо ничего.

Доставка **не менее одного раза** (at-least-once). Хендлеры обязаны быть
идемпотентны.

Разбор рантайма по функциям — что за чем вызывается и какой отказ предотвращает
каждый шаг — в [ARCHITECTURE.ru.md](ARCHITECTURE.ru.md).

## Состав

| Пакет | Содержимое |
|---|---|
| `outbox` | `Message`, `CreateParams`, `Repository`, `Handler`, `Registry`, `Worker`, `Pool` |
| `outbox/postgres` | Реализация `Repository` на GORM/PostgreSQL |
| `outbox/postgres/migrations` | Каноническая DDL в виде `embed.FS` |
| `outbox/metrics` | Стандартные коллекторы Prometheus и готовые `WorkerHooks` |
| `outbox/cronjobs` | `Register` для служебных джоб prune и lag |
| `outbox/testkit` | `FakeRepository` для юнит-тестов |

Конфигурация лежит в `outbox.Settings` (`settings.go`): значения из окружения,
нужные каждому сервису, вместе с дефолтами и обоснованием каждого из них.

## Использование

### 1. Записать строку внутри бизнес-транзакции

```go
ctx = c.dbTransactionManager.Begin(ctx)
// ... бизнес-записи ...

if err := c.outboxRepo.Create(ctx, outbox.CreateParams{
    AggregateType: "deposit_request",
    AggregateID:   depositRequest.ID.String(),
    EventType:     "restriction.counter.update",
    DedupeKey:     "counter:account-deposit-42",
    Payload:       payload,
}); err != nil {
    return err // откат; осиротевшего сообщения не будет
}

return c.dbTransactionManager.Commit(ctx)
```

`Create` сам достаёт транзакцию из `ctx`. Вызов `WithTxFromContext(ctx)` перед
ним по-прежнему допустим, но больше не обязателен — про него слишком легко было
забыть, а забытый он публиковал side effects для откатившихся транзакций.

### 2. Реализовать хендлер на каждый тип события

```go
func (h *CounterUpdateHandler) EventType() string { return "restriction.counter.update" }

func (h *CounterUpdateHandler) Handle(ctx context.Context, msg outbox.Message) error {
    var p CounterUpdatePayload
    if err := json.Unmarshal(msg.Payload, &p); err != nil {
        // Битый payload не станет валидным на ретрае — не тратить на него бюджет.
        return outbox.MarkNonRetryable(err)
    }
    return h.restriction.CountersUpdate(ctx, ...) // ошибки транспорта ретраибельны
}
```

### 3. Собрать пул в composition root

Вложить `outbox.Settings` в cron-настройки сервиса — envconfig зайдёт внутрь и
прочитает теги `CRON_OUTBOX_*` без добавления префикса:

```go
type CronSettings struct {
    // ... джобы самого сервиса ...
    Outbox outbox.Settings
}
```

Дальше рантайм собирается из них:

```go
registry := outbox.NewRegistry()
registry.Register(controllers.NewCounterUpdateHandler(restrictionClient))

settings := config.Cron().Outbox
worker := outbox.NewWorker(outboxRepo, registry, settings.WorkerConfig(tools.OutboxHooks()))
pool := outbox.NewPool(worker, settings.PoolConfig())
// Ёмкость очереди выводится из аренды; см. «Инвариант конфигурации».

g.Go(func() error { return pool.Run(gctx) })
```

### 4. Зарегистрировать служебные cron-джобы

```go
outboxcron.Register(cronManager, outboxRepo, config.Cron().Outbox, tools.SetOutboxLag)
```

Обе джобы — инфраструктура, а не поведение сервиса, поэтому берутся из
`outbox/cronjobs`, а не переписываются заново. Без `outbox.prune` таблица растёт
без ограничений; без `outbox.lag` доставка может остановиться незаметно —
для счётчиков заглохший relay выглядит ровно так же, как простаивающий сервис.

### 5. Применить схему

Не копировать DDL в каталог миграций сервиса. Прогонять
`outbox/postgres/migrations.FS` как второй источник миграций со своей таблицей
истории:

```go
migrator.New(migrator.Config{
    Driver: driver, DSN: dsn,
    MigrationsFS:    outboxmigrations.FS,
    MigrationsTable: "schema_migrations_common",
})
```

Два источника не могут делить одну таблицу истории — они будут спорить за номер
версии. Общие миграции нумеруются из зарезервированного диапазона `9_000_000+`,
поэтому столкнуться с номерами сервиса не могут.

## Инвариант конфигурации

`Lease` — настройка **корректности**, а не производительности.

Сообщение начинает жечь аренду с момента возврата `ClaimDue`, включая время
ожидания диспатча. Если аренда истечёт, пока сообщение ещё стоит в очереди, relay
перезахватит его и отдаст второму воркеру — side effect произойдёт дважды.

Пул выводит собственную ёмкость из аренды:

```
rounds     = (Lease − HandlerTimeout − 1s) / HandlerTimeout
queueSize  = Workers × rounds          // выводится, не настраивается
claim size = queueSize + Workers − in-flight
```

Ни `queueSize`, ни лимит батча не являются настройками. Очередь больше выведенной
даёт истечение аренды на просто стоящих сообщениях; меньше — только режет
пропускную способность. Отдельный размер батча может быть либо ниже бюджета
захвата, где он просто душит, либо выше, где не делает ничего. Настройки, которые
могут только навредить или ничего не дать, настройками не являются.

`HandlerTimeout` заслуживает такой же придирчивости с другой стороны. Он выглядит
бесплатным запасом прочности, но им не является: он задаёт пол для `Lease`, а
значит и время восстановления после падения; ограничивает, сколько один зависший
вызов держит воркера; и чем он больше, тем меньше слотов очереди даёт та же
аренда. Размер берётся из хвостовой латентности транспорта. account-service и
pay-service публикуют в RabbitMQ и ходят в restriction-service по gRPC, оба
укладываются в 200 мс, поэтому у обоих стоит 2 с — порядок запаса, а не два.

Дефолты лежат в `outbox.Settings`, а не в каждом сервисе, по конкретной причине:
внедрившие паттерн сервисы делят одну панель и один набор алертов, а те
описывают все сервисы корректно только пока значения совпадают. Переопределять
через окружение, когда сервису действительно нужно другое число, — и записывать,
почему.

Что стоит знать до тюнинга:

- На дефолтах (`Lease=8s`, `HandlerTimeout=2s`, `Workers=4`) пул держит
  одновременно максимум 12 сообщений. Это осознанный потолок, выведенный из
  аренды, а не узкое место, которое надо убрать.
- Сжатие `HandlerTimeout` расширяет этот потолок: именно на него делится бюджет
  очереди. Переход с 5 с на 2 с поднял потолок с 8 до 12, а замеренную пропускную
  способность с 289 до 432 msg/s на свободном хендлере.
- `NewWorker` поднимает `Lease` до `HandlerTimeout + 1s`, если переданное
  значение меньше, и пишет warning. Такой warning означает, что конфигурация
  попросила небезопасное — хендлер, способный пережить собственную аренду.

## Пропускная способность

Замерено сквозняком на реальном PostgreSQL с конфигурацией, которую везёт
account-service (`Lease=8s`, `HandlerTimeout=2s`, `RelayInterval=500ms`).
Воспроизвести:

```bash
go test -tags=dbstress ./outbox/postgres -run Throughput -v -timeout=15m
```

| Хендлер | Воркеры | Пропускная способность | Дублей |
|---|---|---|---|
| свободный | 4 | 432 msg/s | 0% |
| 5 мс | 4 | 436 msg/s | 0% |
| 20 мс | 4 | 182 msg/s | 0% |
| 20 мс | 16 | 715 msg/s | 0% |
| 20 мс | 24 | 1086 msg/s | 0% |
| 20 мс | 32 | 1463 msg/s | 0% |

Числа получены на ноутбучном Docker PostgreSQL, поэтому читать надо *форму*, а не
абсолютные значения — продакшн-железо будет другим. Что переносится:

- **Пропускная способность растёт почти линейно по `Workers`** минимум до 32.
  Это единственный рычаг, который работает.
- **На малом числе воркеров упирается в базу, а не в хендлер.** Свободный хендлер
  и хендлер на 5 мс дают одинаковые ~435 msg/s при четырёх воркерах: пол — один
  коммит обновления статуса на сообщение.
- **Ни одного дубля и ни одного dead-letter ни на одной нагрузке.**
  Back-pressure поглощает давление вместо того, чтобы деградировали гарантии.
- **Умножается на число подов.** У каждого инстанса свой пул, а `SKIP LOCKED`
  разводит строки между ними.

Два структурных ограничения:

1. **Потолок in-flight** — `queueSize + Workers` сообщений одновременно. На
   дефолтах это 12. Выводится из аренды, а не является промахом тюнинга.
2. **Ёмкость воркеров** — `Workers / длительность хендлера`, снизу подпёртая
   коммитом на каждое сообщение.

Восстановление после падения стоит одну аренду: сообщения убитого пода лежат в
`processing`, пока не пройдёт `locked_until`. Это вторая причина держать аренду
короткой.

`RelayInterval` потолком **не является**. Relay продолжает захватывать, пока
разбирается бэклог, и уходит спать до следующего тика только когда захват вернул
меньше запрошенного. На старте он делает проход сразу, а не простаивает интервал,
и при насыщении ждёт слот 25 мс вместо возврата к тику.

### На объёмах ограничивает не доставка, а рост таблицы

Доставка справляется задолго до того, как справится хранилище. При устойчивом
потоке `R` msg/s 48-часовой retention для доставленных держит `R × 172800` строк:

| Устойчивый поток | Строк при retention 48 ч |
|---|---|
| 20 msg/s | ~3.5 млн |
| 100 msg/s | ~17 млн |
| 300 msg/s | ~52 млн |

При JSONB-payload в несколько сотен байт это десятки гигабайт в бизнес-базе — и
каждая вставка лежит на критическом пути той транзакции, которая её пишет.

**Рычаг — retention, а не партиционирование.** Партиционирование по времени —
обычный ответ для таблицы такой формы, и здесь оно не работает: PostgreSQL
требует, чтобы уникальное ограничение включало все колонки ключа
партиционирования, поэтому при партиционировании по `created_at` глобальный
`UNIQUE (dedupe_key)` невозможен.

```
ERROR:  unique constraint on partitioned table must include all partitioning columns
DETAIL:  UNIQUE constraint on table "ob" lacks column "created_at" ...
```

Партиционирование по `hash(dedupe_key)` ограничение сохраняет, но не даёт
`DROP PARTITION` по времени — а это единственная причина партиционировать. То
есть партиционирование стоит гарантии дедупликации и не даёт ничего, пока сама
гарантия не переедет куда-то ещё.

Поэтому retention разделён надвое: два типа строк служат разным целям, и общее
окно заставляло бы выбирать между диском и окном разбора.

| Строки | По умолчанию | Почему |
|---|---|---|
| `delivered` | 48 ч | Именно они забивают диск. Плюс фенс дедупликации на вставке |
| `dead` | 7 дней | Окно для разбора: успеть заметить, разобраться и починить |

Prune ходит ежечасно, а не раз в сутки: суточная уборка копит день строк и удаляет
их одним всплеском — ровно та форма, которая создаёт нагрузку на vacuum.

Retention для `dead` — окно **разбора**, а не реплея. Реплей механически
безопасен только пока жив собственный ключ идемпотентности у получателя (48 ч у
обоих текущих потребителей), потому что dead-сообщение не доказывает, что эффект
не применился: хендлер может отработать успешно, а запись статуса — упасть, и так
несколько раз, пока перезахваты не исчерпают бюджет. За пределами этого окна
оператор всё равно обязан сверить состояние вручную, так что лишний retention
ничего не даёт.

И он же кое-что отнимает. `dedupe_key` мёртвой строки по-прежнему блокирует
повторную вставку, поэтому каждый лишний день хранения — это ещё один день, когда
легитимный повторный прогон бизнес-пути не может пересоздать этот side effect.
Долгое хранение мешает восстановлению, а не помогает.

Не опускайте retention для `delivered` ниже TTL дедупликации у получателя для тех
типов событий, у чьего потребителя нет собственного фенса. Защита — это большее
из двух окон: пока строка outbox жива, дубль отсекается на вставке; после — его
может остановить только ключ идемпотентности у получателя. У обоих текущих
потребителей он живёт 48 ч, отсюда и дефолт.

## Поведение при отказах

| Отказ | Что происходит |
|---|---|
| Хендлер вернул ошибку | `failed`, ретрай с экспоненциальным backoff, бюджет расходуется |
| Downstream лежит часами | Копится в `failed`, растёт метрика лага, dead-letter примерно через 4 ч на дефолтах |
| Под убит посреди хендлера | Аренда истекает, перезахватывает другой инстанс, **attempts инкрементится** — краш-петля завершается |
| БД недоступна | Relay логирует и пробует на следующем тике; ничего не потеряно, ничего не доставлено |
| `MarkDelivered` упал после успешного хендлера | Переотправка — хендлер выполнится дважды. Отсюда требование идемпотентности |
| Паника в хендлере | Сразу `dead`, срабатывает `OnDead` |
| Паника в relay | Перехвачена, сообщается через `OnClaimError`; доставка стоит до следующего тика, остальной сервис продолжает работать |
| SIGTERM | Воркеры дочищают очередь, статусы в полёте дописываются (неотменяемый контекст) |

Под устойчивой нагрузкой пул давит back-pressure, а не растёт: горутин ровно
`Workers + 1`, память ограничена `queueSize` сообщений. Растёт вместо этого
таблица — для того и нужны `Prune` и метрика лага.

## Тюнинг

Меняйте по одному параметру и смотрите на `outbox_oldest_pending_age_seconds`.

| Симптом | Что менять |
|---|---|
| Лаг растёт, длительность хендлера низкая | Поднять `Workers` |
| Лаг растёт, длительность высокая | Чинить downstream; воркеры лишь распараллелят ожидание |
| Нужен больший потолок in-flight | Поднять `Lease` или снизить `HandlerTimeout` — глубина очереди это `(Lease−HandlerTimeout−1s)/HandlerTimeout` кругов |
| Таймауты в `last_error` | Поднять `HandlerTimeout` к реальной хвостовой латентности, и `Lease` вместе с ним |
| Медленное восстановление после падения | Снизить `Lease` — это задержка до перезахвата другим подом |
| Таблица растёт | Сократить `OutboxDeliveredRetention`, но не ниже TTL дедупликации у получателя |
| Простаивающий сервис слишком часто опрашивает | Поднять `RelayInterval`; он влияет только на то, как быстро простаивающий пул заметит работу |

На старте пишется warning каждый раз, когда переданное значение было
переопределено. Warning означает, что конфигурация попросила небезопасное — его
надо прочитать, а не заглушить.

## Риски в продакшене

- **Таблица живёт в бизнес-базе.** Депозит не закоммитится, если вставка в outbox
  упала. В этом и смысл — но это же означает, что раздувание outbox становится
  проблемой доступности бизнес-операций. Держите `Prune` работающим и заведите
  алерт на размер таблицы.
- **`Prune` удаляет батчами по 5000** и безопасен рядом с воркерами, но первый
  прогон на давно не чищенной таблице будет долгим. Прогоните его вручную в окно
  обслуживания, прежде чем включать cron на существующей таблице.
- **Защита от дублей истекает вместе с retention** (см. выше). Retention короче
  TTL дедупликации у получателя сужает реальную гарантию.
- **Порядок не сохраняется.** Сообщения захватываются по `next_attempt_at` и
  обрабатываются конкурентно. Если два события по одному агрегату обязаны
  примениться по порядку, outbox этого не обеспечит.
- **Мёртвое сообщение невидимо без алерта.** Автоматического реплея нет.
  `increase(outbox_dead_total[1h]) > 0` — единственное, что стоит между
  dead-letter уведомлением о выплате и тем, что этого никто не заметит.
- **Cron-джобы выполняются на каждом поде.** У платформенного cron нет выбора
  лидера, поэтому `Prune` и снятие лага идут по разу на реплику. `Prune`
  захватывает свои батчи через `FOR UPDATE SKIP LOCKED`, поэтому конкурентные
  уборщики делят работу, а не блокируют друг друга; снятие лага — это чтение, и
  каждый под просто сообщает одно и то же значение.

## Семантика доставки

| Результат хендлера | Итог |
|---|---|
| `nil` | `delivered` |
| ошибка | `failed`, ретрай с экспоненциальным backoff (±10% джиттера) |
| `MarkNonRetryable(err)` | сразу `dead`, бюджет не тронут |
| неизвестный `event_type` | `dead` (оборачивает `ErrNonRetryable`) |
| attempts достигли `MaxAttempts` | `dead` |
| паника | `dead` — паника это дефект кода, а не транзиентный сбой |

Воркер, потерявший аренду (его сообщение перезахватили после истечения),
получает `ErrLeaseLost` от обновления статуса и отбрасывает свой результат вместо
того, чтобы затереть состояние нового владельца.

Перезахваты по протухшей аренде **расходуют бюджет ретраев**. Сообщение, которое
каждый раз убивает своего воркера — OOM, паника, вытеснение пода — иначе
перезахватывалось бы вечно; вместо этого оно уходит в `dead` после `MaxAttempts`
перезахватов.

## Идемпотентность и её границы

`dedupe_key` уникален, поэтому повторная вставка молча игнорируется. Эту гарантию
ограничивают две вещи, и обе важны при выборе окна retention:

1. **Retention.** `Prune` удаляет доставленные строки после окна хранения,
   унося ключ с собой. После этого повторный прогон того же бизнес-пути вставит
   то же логическое событие заново.
2. **TTL у получателя.** Там, где принимающий сервис дедуплицирует —
   restriction-service держит `limit_counter_idempotency_keys`,
   notification-service держит `notification_dedupe_keys`, оба по 48 ч — именно
   этот TTL и есть реальное окно защиты.

   Продюсеры должны передавать `dedupe_key` строки outbox тем потребителям,
   которые умеют фенсить. account-service делает это для `notification.push`, где
   ретрай иначе отправил бы пользователю второе уведомление.

Хендлеры обязаны быть идемпотентны независимо от этого. Ретраи — это норма, а не
редкий случай.

## Наблюдаемость

Используйте `outbox/metrics`, а не собственные коллекторы:

```go
m, err := outboxmetrics.New("account_service", prometheus.DefaultRegisterer)
worker := outbox.NewWorker(repo, registry, outbox.WorkerConfig{Hooks: m.Hooks(), ...})
// и в cron лага: m.SetLag(ages)
```

Имена метрик — это контракт с дашбордами и правилами алертов. Зафиксированные в
одном месте, они позволяют держать одну панель и один набор алертов на все
сервисы; переименование после первой выкатки рвёт историю за каждым графиком.

`WorkerHooks` (`OnDelivered`, `OnFailed`, `OnDead`, `OnHandlerDuration`) ложатся
напрямую на счётчики и гистограмму Prometheus.

Одни счётчики не обнаружат вставший relay: он просто перестаёт их инкрементить,
что выглядит ровно как простаивающий сервис. Снимайте `OldestPendingAge` по cron
в gauge и алертите на него. Сбрасывайте gauge на каждом замере — типы событий с
разобранным бэклогом отсутствуют в карте, а `GaugeVec` иначе будет вечно
показывать последнее значение.

`OnClaimError` и `OnLeaseLost` закрывают два пути отказа, которых хуки исходов не
видят:

- **`OnClaimError`** — relay не смог захватить работу. Это единственный
  немедленный сигнал, что доставка встала полностью, и он не дублирует метрику
  лага: снятие лага читает ту же базу, поэтому её недоступность оставляет gauge
  замороженным на последнем значении, а не растущим. Без этого счётчика отказ
  базы выглядит ровно как простаивающий сервис.
- **`OnLeaseLost`** — обновление статуса отброшено, потому что сообщение уже
  перезахватил другой воркер. Не ошибка, но устойчивая частота означает, что
  работа делается дважды и выбрасывается: пул перегружен или аренда слишком
  коротка.

Рекомендуемые алерты:

- `increase(outbox_claim_errors_total[5m]) > 0` — доставка встала
- `outbox_oldest_pending_age_seconds > 300` — доставка отстаёт
- `increase(outbox_dead_total[1h]) > 0` — нужен человек
- устойчивый `rate(outbox_failed_total[5m])` — нездоров downstream
- устойчивый `rate(outbox_lease_lost_total[5m])` — пул перегружен

## Runbook по DLQ

`status = 'dead'` означает, что доставка прекращена. Автоматически ничего не
ретраится.

**Триаж:**

```sql
SELECT event_type, count(*), max(created_at) AS newest
FROM outbox_messages
WHERE status = 'dead'
GROUP BY event_type
ORDER BY count DESC;
```

**Разбор конкретного отказа:**

```sql
SELECT id, aggregate_type, aggregate_id, dedupe_key, attempts, last_error, payload
FROM outbox_messages
WHERE status = 'dead'
ORDER BY created_at DESC
LIMIT 20;
```

`last_error` различает две причины: неретраибельную ошибку (битый payload,
незарегистрированный `event_type`, нарушение бизнес-инварианта) и исчерпание
бюджета ретраев (зависимость лежала дольше, чем позволял бюджет).

**Реплей после устранения причины** — только когда вы убедились, что хендлер
теперь отрабатывает и что повтор безопасен для этого side effect:

```sql
UPDATE outbox_messages
SET status = 'pending', attempts = 0, next_attempt_at = NOW(),
    locked_by = NULL, locked_until = NULL, last_error = NULL
WHERE id = ANY($1::bigint[]);
```

Реплеить по явному списку id, никогда не сплошным `WHERE status = 'dead'`: в
мёртвом множестве обычно смешаны сообщения, безопасные для повтора, и те, что
мертвы по делу.

**Не реплеить** сообщения с незарегистрированным `event_type`, пока не появится
хендлер — они просто умрут снова. Сначала проверьте регистрации в `Registry`.

## Схема

Каноническая DDL лежит в `outbox/postgres/migrations` как `embed.FS`. Применяйте
её прямо оттуда, а не копируйте в каталог миграций сервиса, где копия разойдётся:

```go
migrator.New(migrator.Config{
    Driver: "postgres", DSN: dsn,
    MigrationsFS:    outboxmigrations.FS,
    MigrationsTable: "schema_migrations_common", // своя история
})
```

Общий источник выполняется отдельным мигратором со своей таблицей истории,
поэтому его версии не связаны с версиями сервиса и столкнуться не могут. В тестах
её же можно загрузить через `postgrestest.OpenConfig.MigrationsFS`.

Эти файлы используют зарезервированную полосу версий `9 000 000+`. golang-migrate
ключует миграции по числовому префиксу и отвергает дубли, поэтому общая миграция
с номером `0001` конфликтовала бы с первой собственной миграцией каждого сервиса
и делала бы комбинацию FS+Dir неприменимой.

## Тестирование

`outbox/testkit.FakeRepository` — реализация `Repository` в памяти для
юнит-тестов. Она повторяет значимую семантику SQL — дедупликацию, владение
арендой, расход бюджета при перезахвате — и добавляет тестовые хелперы:

- `ExpireLease(id)` — смоделировать воркера, умершего посреди обработки
- `MakeDue(id)` — приблизить запланированный ретрай вместо ожидания
- `FailMarkDelivered` — проверить путь переотправки после упавшей записи статуса

Поведение репозитория покрыто против настоящего контейнера с PostgreSQL через
`testkit/postgrestest`; для `go test ./outbox/...` нужен Docker.
